## 3. 实验结果

### 3.1 K=25 vs K=50 同机配对（核心结论）

16 个最难任务，种子取两边实际交集（平均 46 个/任务，744 个配对回合）：

| setting | K=25 | K=50 | 差 | 显著性 |
|---|---|---|---|---|
| clean | 54.84% | 55.51% | −0.67pp | McNemar χ²=0.09，不显著 |
| randomized | 23.79% | 19.76% | **+4.03pp** | χ²=6.67，**p<0.05 显著** |

与上一版在 GH200 上的独立配对实验（randomized +4.5pp）一致，互印证。

### 3.2 三方对比与效应分解

| | clean | randomized |
|---|---|---|
| K 效应（同机 K25 − K50） | −0.64pp | **+4.24pp** |
| 环境效应（同 K50，x86 − GH200） | **+11.14pp** | −0.97pp |

**clean 的平台差异远大于参数差异**：同一 checkpoint、同一 K 值，仅换平台就差 11pp。

### 3.3 环境一致性校准

用官方权重 `robbyant/lingbot-vla-v2-6b-robotwin`（配官方 norm）在本机跑 6 任务，平均 ≈80%，与官方公布 x86 基准 83.5% 相差 3.2pp 以内，确认本机环境正常。

## 4. 关键发现

1. **randomized 上 K=25 确实更优**，两个独立实验（x86 与 GH200）方向与幅度一致。
2. **clean 上 K=25 与 K=50 等价**，之前"K=25 在 clean 也更好"的印象来自跨环境对比，是混杂因素。
3. **aarch64（GH200）的 Vulkan 渲染显著拖累 clean 场景**，对 randomized 几乎无影响。
4. **提交包缺 `lingbotvla_cli.yaml` 是上一版的隐性缺陷**，官方复测会遇到 `FileNotFoundError`。
5. 官方权重的 HF 仓库目录结构（`checkpoints/global_step_xxxxx/hf_ckpt` + 仓库根 `lingbotvla_cli.yaml`）就是提交包应该对齐的形态。

## 5. 问题与教训

### 5.1 ⚠️ 提交次数限制（最重要，必须制度化）

**规则原文**：「初赛期间累计可提交三次结果（非每日三次），提交机会应审慎规划使用。」

**本次问题**：在提交包刚打包完成、尚未在所有渠道完成交叉验证时，就直接上传了 OSS。上传是否已计入三次配额、是否需要在天池页面二次确认，事前没有核实清楚。**如果上传即计次，这次可能已经消耗了三分之一的机会。**

**根因**：
- 「打包完成」被等同于「可以提交」，缺少**独立的提交准入检查**；
- 自动化脚本可以一路做到 OSS 上传，中途没有强制的人工确认闸门；
- 没有在项目开始时就把「3 次机会」当成硬约束写进流程。

**改进措施（下次必须执行）**：
1. **把提交设计成独立、显式、不可自动触发的最后一步**。所有脚本默认只做到「生成待提交包 + 校验报告」，上传命令必须人工逐条确认执行。
2. **提交前固定执行一份准入清单**（缺一不可）：
   - [ ] 本地文件 sha256 与源一致
   - [ ] 解压后文件名无乱码、46/46 文件结构正确
   - [ ] 模拟官方复测路径解析通过（`CKPT`、`lingbotvla_cli.yaml`）
   - [ ] `results.json` schema / team_id / 50×100 合规
   - [ ] README 与复现报告已更新到与本次配置一致
   - [ ] 天池页面确认剩余提交次数
3. **把剩余次数写进项目 README 顶部**，每次提交后立即扣减并记录。
4. **区分"测试上传"与"正式提交"**：如需验证 OSS 通路，用一个明显不参与评审的小文件（如 `_test.bin`）在**独立路径**测试，不要用正式文件名。

### 5.2 无卡模式 2GB 内存无法完成大文件云端上传

23 GB 上传连续失败三次：

| 方式 | 结果 |
|---|---|
| hf_transfer 并发 8 | 1.86 GB 处进程消失 |
| hf_transfer 并发 2 | 2.07 GB 处进程消失 |
| HF Xet 协议 | 2.30 GB 处进程消失 |

`memory.events` 显示 `max` 触发 87 万次（持续触碰 2GB 上限），`oom_kill=0`（非 OOM killer，而是内存压力下进程异常终止）。

**最终解法**：用 `oss2` SDK 手动 multipart 上传，16 MB 分片顺序传输，内存稳定 2045 MB，22.5 分钟完成。

**教训**：
- 大文件传输必须**流式 + 小分片**，分片大小控制在内存上限的 1/100 量级；
- 不要依赖高层封装的自动并发（hf_transfer / Xet 的缓冲策略对 2GB 环境不友好）；
- 无卡模式只适合轻量操作（下载、文本处理），**不要用于大文件上传**。

### 5.3 提交包结构缺陷：缺 `lingbotvla_cli.yaml` 与目录被压平

**现象**：上一版提交包 `03_模型权重/checkpoint/` 只有权重文件，缺 `lingbotvla_cli.yaml`，且 `main_aug/checkpoints/global_step_51456/hf_ckpt` 四层目录被压平成一层的 `checkpoint/`。

**后果**：推理服务按 `Path(model_path).parent.parent.parent / 'lingbotvla_cli.yaml'` 查找训练配置，直接 `FileNotFoundError`。

**根因**：打包时只复制了 `hf_ckpt/` 目录**内容**，没有带上同级文件，也没有保留层级。

**教训**：
- 打包逻辑应该是「复制整个训练输出目录（`main_aug/`）」，而不是「复制权重文件夹内容」；
- 打包后必须**用官方复测的视角**做一次路径解析验证（模拟 `eval.sh` 的 `$HERE/../...` 和推理代码的三层 parent 推导）；
- 官方权重的 HF 仓库结构就是标准答案，可直接对照。

另外发现官方 `lingbotvla_cli.yaml` 的 `joints` / `norm_type` 是**字面量字符串**（`"{'arm.position': 14}"`）而非 YAML dict，否则 `ast.literal_eval` 会报错——这类隐式约定要靠读代码确认，不能靠猜。

### 5.4 误删评测结果（靠日志重建挽回）

**问题**：准备配对实验时误执行 `rm -rf eval_k25/randomized/run/eval_results`，删掉了 randomized 的逐种子明细。

**挽回**：`eval_logs/*.log` 中每集都有 `TIMING task=xxx seed=100000 succ=1 ...` 行，据此重建 4981 条逐种子记录，与 `results.json` 的 50/50 任务、2467 成功**完全一致**。

**教训**：
- 删除类操作前必须 `echo` 出待删路径并确认；
- **逐回合日志里带 seed + 结果**是一个极有价值的冗余设计，应在评测阶段默认开启；
- 汇总文件（`results.json`、`stats.txt`）要单独备份，不要只依赖明细目录。

### 5.5 缺少 hang 监控导致 15 小时浪费

**问题**：8 个仿真进程中有 4 个在 10-24 凌晨静默挂起（CPU 5-10% 空转），直到 14.5 小时后才被发现。其间有效吞吐从 424 集/小时掉到 20 集/小时。

**解法**：加两级看门狗——
- 任务级：日志静默 > 600 秒 → 杀掉该 sim，launcher 自动重启并断点续跑；
- 全局级：主流程/推理服务存活检查 + 15 分钟窗口速率告警；
- 全部任务同时 hang 连续 2 轮 → 判定推理服务僵死，重启整个流程。

**教训**：
- 长时间评测必须配「日志静默」检测，不能只看进程是否存在（进程活着但没进展最危险）；
- 静默阈值要与该任务的最慢单集耗时挂钩（慢任务 117 秒/集，阈值不能设太小）。

### 5.6 时间估算系统性偏乐观

**问题**：三次估算都偏短——
- K=25 全量估 24 小时，实际约 30 小时；
- K=50 配对估 2.5 小时，实际约 4 小时；
- 本地下载估 20 分钟，实际约 40 分钟。

**根因**：
- 用**早期快任务样本**估算整体速率（前 8 个 slot 恰好都是 400 步的快任务，得出 765 集/小时；后期慢任务多，实际 326 集/小时）；
- 低估 K 值变化对推理开销的影响（K 从 50 降到 25，推理次数翻倍）。

**教训**：
- 估算用**最慢任务耗时 ÷ 并行数**做下限，而不是用前 N 分钟的吞吐外推；
- 报时间给区间，不给单点值。

### 5.7 跨环境对比的混杂因素

**问题**：最初把「x86 K=25 78.18% vs GH200 K=50 58.98%」当成「K=25 带来 +19pp」，实际上是环境与参数两个变量同时改变。

**教训**：
- 任何提升结论必须**单变量**验证（同机、同种子、配对）；
- 换平台后要重做基线，不能跨平台比绝对值。

### 5.8 环境校准实验的配置错配

**问题**：用官方后训练权重做环境校准时，喂了 clean-only 的 `robotwin_clean.json` 归一化统计，导致 `click_bell` 1%、`lift_pot` 2%，一度误判「环境偏严 −33.8pp」。换成官方 `robotwin.json` 后恢复 86.7% / 100%。

**教训**：
- 权重、robot_config、norm_stats 是**三位一体**，跨 checkpoint 复用必须三件套一起换；
- 看到「部分任务接近 0、部分任务正常」的分布，优先怀疑归一化错配，而不是环境问题。

### 5.9 GitHub 无法承载 23 GB 权重

**约束**：GitHub LFS 单文件上限 2 GB、免费仓库 5 GB，23.16 GB 单文件 zip 无法上传。

**正确做法**（本次采用）：
- GitHub 放代码 + 结果 + 文档（约 250 KB）；
- HuggingFace 放完整包；
- GitHub README 顶部显式链接 HF 权重。

### 5.10 数据迁移与解压编码

**问题**：zip 用 `unzip` 解压中文文件名出现乱码目录（`#U5177#U8eab...`），24 GB 权重落到了错误目录。

**解法**：Python `zipfile.extractall()`（打包含 UTF-8 flag，解压正常）；打包也用 Python `zipfile` 并确认 `flag_bits & 0x800` 全为 1。

**教训**：跨平台中文文件名必须走 UTF-8 标志位，不要依赖系统默认编码。
